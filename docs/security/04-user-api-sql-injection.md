## 概要

`apps/web/public/api/user.php` の `update` アクションは、ユーザー行の再取得に SQL を `SQLite3::escapeString` による文字列結合で組み立てている。同一ファイルの他のすべてのクエリはプリペアドステートメント（`prepare` + `bindValue`）を使用しており、この 1 箇所だけが古い書き方で危険なパターンの置き場になっている。

## 問題箇所

`apps/web/public/api/user.php:73`

```php
$row = $db->querySingle("SELECT * FROM users WHERE id='" . SQLite3::escapeString($user['id']) . "'", true);
```

## 脅威・再現手順

- `SQLite3::escapeString()` は `'` と `\` しかエスケープせず、他の脅威（マルチバイト文字の符号化違いや、文脈によってはその他のメタ文字）に対する堅牢な防御ではない。
- 現状 `$user['id']` はセッションから得たサーバー生成の `u_<hex>`（`bin2hex(random_bytes(12))`）であり混入不可なので、今日のところ直接の侵害は不可能。
- しかし、他の全処理がプリペアドステートメント統一されている中でこの箇所だけ文字列結合が残ると、将来 id の生成元がユーザー入力を含むように変わった際に SQL インジェクションに直結する。

## 影響

- 潜在的な SQL インジェクション（現在は到達不能だが、コード保守の観点で危険な臭い）。
- 一貫性の欠如（レビュー・保守性低下）。

## 推奨対応

- 他のアクションと同様に `prepare` + `bindValue(':id', $user['id'], SQLITE3_TEXT)` に書き直す。
- リポジトリ全体で「SQL は常にプリペアドステートメント」を徹底する lint/方針を確認。

## 検証方法

- `update` アクションで `querySingle` の文字列結合が無くなり、プリペアドステートメント経由になっていることを確認。
- （オプション）静的解析で文字列結合 SQL を検出するルールを追加。

## 優先度

low（現時点では到達不能な潜在缺陷。他処理との一貫性維持のための修正）
